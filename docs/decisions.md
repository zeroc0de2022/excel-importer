# Ключевые решения

Короткие записи о том, *почему* проект устроен именно так: что выбрано, какие были альтернативы
и чем за это заплачено. Каждый раздел можно пересказать за 1–2 минуты.

---

## 1. Батч с джобой-читателем, которая сама добавляет чанки

**Задача.** Файл надо разобрать через джобы по 1000 строк, а в конце — один раз собрать отчёт.

**Решение.** При загрузке создаётся `Bus::batch` всего с одной джобой — `ReadImportFile`. Она
читает файл потоково и каждые 1000 строк вызывает `$this->batch()->add(new ProcessImportChunk(...))`.
Колбэк `finally()` собирает `result.txt` и итоговые счётчики.

**Почему так.**
- Файл читается **один раз** и потоково: не нужно ни держать все 100 чанков в памяти,
  чтобы передать их в `Bus::batch([...])`, ни перечитывать файл в каждой джобе со смещения
  (это O(n²) по чтению).
- Батч не может закончиться раньше времени: пока `ReadImportFile` выполняется, у батча есть
  незавершённая джоба, а новые чанки увеличивают счётчик `pending_jobs` до её окончания. Поэтому
  `finally()` срабатывает строго после последнего чанка. Так устроен «loading batches» из
  документации Laravel.
- Пустой файл обрабатывается без особых случаев: батч из одной джобы просто завершается.
- `allowFailures()`: один сломанный чанк не останавливает остальные; импорт получает статус
  `failed`, но отчёт всё равно собирается.

**Альтернативы.**
- `Bus::chain` — чанки строго по очереди, без параллелизма.
- Джобы без батча + счётчик «сколько осталось» — по сути самописный батч.
- Готовый queued-импорт из пакета (Laravel Excel) — задание прямо требует сделать это самим.

**Цена.** Данные чанка (1000 строк, ~40 КБ) лежат в payload джобы в Redis. Для больших объёмов
или нескольких серверов можно класть чанки в S3 и передавать в джобе только путь.

## 2. Потоковое чтение xlsx

**Проблема исходной версии.** `IOFactory::load()` + `toArray()` из PhpSpreadsheet строит в памяти
всю книгу, причём прямо в HTTP-запросе. Память растёт вместе с размером файла.

**Решение.** [OpenSpout](https://github.com/openspout/openspout) читает xlsx как поток XML, строку
за строкой. `SpreadsheetReader::rows()` — генератор `номер строки => [id, name, date]`.

**Подводный камень, который пришлось найти.** xlsx хранит текст в общей таблице строк
(shared strings), а Google Sheets кладёт туда *каждую* текстовую ячейку. OpenSpout по умолчанию
закладывает 12 КБ на строку и при `memory_limit=256M` переключается на кэш в файлах. На файле
из задания (60 000 строк, 128 000 уникальных строк) это давало **22 с** на одно только чтение.
Свой `CachingStrategyFactory` держит таблицу в памяти до 1 млн строк: **1,7 с, пик 12 МБ**.
Выше миллиона — снова файловый кэш, чтобы память оставалась ограниченной.

**Результат.** Пик памяти 38 МБ и на 100 000, и на 300 000 строк (см. бенчмарк в README).

**Почему `SHOULD_PRESERVE_EMPTY_ROWS`.** Тогда ключ итератора равен настоящему номеру строки
в Excel, и номера в отчёте совпадают с тем, что видит пользователь, даже если в файле есть
пустые строки.

## 3. `INSERT … ON CONFLICT DO NOTHING` вместо `exists()` + `create()`

**Проблема исходной версии.** Для каждой строки `Row::where(...)->exists()`, затем `create()`:
2000 запросов на чанк и гонка — два воркера одновременно видят «нет такого id», оба вставляют,
один падает на уникальном индексе, джоба ретраится и **счётчик прогресса удваивается**.

**Решение.** Одна вставка на чанк: `DB::table('rows')->insertOrIgnore($records)`, в PostgreSQL это
`INSERT … ON CONFLICT DO NOTHING`. Решение «чья строка первая» принимает база, а не PHP.

- **Почему `DO NOTHING`, а не upsert (`DO UPDATE`).** Задание: «строки с одинаковым id не заменять,
  оставлять импортированную первой». Upsert перезаписал бы старую строку.
- **Почему без явной транзакции.** Один SQL-запрос в PostgreSQL и так атомарен: либо вставлены
  все строки чанка, либо ни одна. Транзакция вокруг одного запроса ничего не добавляет.
- **Защита от дедлоков.** Два параллельных чанка с пересекающимися id могут захватить блокировки
  в разном порядке (A: 5, потом 7; B: 7, потом 5) → дедлок. Строки сортируются по id перед
  вставкой, порядок блокировок везде одинаковый.
- **Как узнать, какие строки — дубликаты.** После вставки одним `SELECT … WHERE id IN (...)`
  берутся владельцы этих id. Если строку создал другой импорт или другая строка файла — это
  дубликат.

**Что значит «первая».** При нескольких воркерах «первая» — это первая *вставленная* строка, что
буквально соответствует формулировке задания («импортированную первой»). Внутри одного чанка
побеждает меньший номер строки. С одним воркером (по умолчанию в `compose.yaml`) чанки идут по
порядку, и порядок совпадает с порядком в файле. Если нужен строгий порядок файла при нескольких
воркерах — либо `Bus::chain` (минус параллелизм), либо сначала дедупликация в читающей джобе.

## 4. Идемпотентные ретраи

Джоба может выполниться повторно: воркер упал, истёк таймаут, сетевой сбой. Повтор не должен ни
задвоить строки, ни задвоить прогресс, ни испортить отчёт.

| Что защищаем | Как |
|---|---|
| Строки в `rows` | `ON CONFLICT DO NOTHING` — повторная вставка ничего не меняет |
| Счётчики прогресса | Lua-скрипт в Redis: `SADD import:{id}:chunks <номер>`; если номер уже был — ничего не делаем, иначе `INCRBY` счётчиков и `ZADD` ошибок. Redis выполняет скрипт атомарно |
| Отчёт | ошибки лежат в sorted set, член = текст строки отчёта, повторный `ZADD` того же члена ничего не добавляет |
| Отчёт после сбоя «между БД и Redis» | строки хранят `import_id` и `row_number`; при повторе строка, созданная этим же импортом из этой же строки файла, считается своей, а не дубликатом |

Последний случай — самый интересный на собеседовании. Две системы хранения (PostgreSQL и Redis)
нельзя обновить одной транзакцией. Если воркер упал после вставки в БД, но до записи в Redis,
повтор снова вставит те же id и получит «конфликт». Без `import_id` + `row_number` эти строки
попали бы в отчёт как дубликаты самих себя. Решение не в распределённой транзакции, а в том,
чтобы **каждая сторона была идемпотентной сама по себе**. Этот сценарий покрыт интеграционным
тестом.

`ReadImportFile` имеет `tries = 1`: повторное чтение добавило бы все чанки второй раз. Сами чанки
это пережили бы (см. таблицу), но нет смысла делать лишнюю работу.

## 5. Прогресс в Redis

**По заданию:** уникальный ключ + количество обработанных строк → `import:{uuid}:processed`,
увеличивается через `INCRBY` внутри Lua-скрипта.

Рядом лежат `:failed`, `:chunks` (множество засчитанных чанков) и `:errors` (sorted set строк
отчёта, score = номер строки — сортировка бесплатная).

- **Почему не счётчик в PostgreSQL.** `UPDATE imports SET processed = processed + 1000` из
  параллельных воркеров — это конкуренция за одну строку таблицы. `INCRBY` в Redis — O(1) без
  блокировок. В БД итоговые счётчики пишутся один раз, в конце.
- **Пока импорт идёт,** API читает счётчики из Redis; после завершения — из таблицы `imports`.
  Ключи Redis живут ещё сутки (`EXPIRE`), потом удаляются сами.
- **Отчёт** собирается в `finally()` страницами по 1000 строк (`ZRANGE`) и пишется в файл потоково:
  даже отчёт на миллион строк не загружается в память целиком.

## 6. Событие на чанк, а не на строку

Задание просит транслировать событие о создании записи через Laravel Echo. Исходная версия
отправляла `ShouldBroadcast`-событие **на каждую строку**, то есть на каждую строку ставилась ещё
одна джоба в очередь: 100 000 строк → 100 000 лишних джоб и 100 000 WebSocket-сообщений каждому
открытому браузеру.

Сейчас `RowsCreated` отправляется **раз на чанк** (100 событий на 100 000 строк) и несёт то, что
нужно интерфейсу: сколько строк создано, сколько обработано и сколько с ошибками.

- **`ShouldBroadcastNow`** — событие уходит прямо из воркера, без ещё одной джобы в очереди.
- **`rescue()` вокруг отправки** — если Reverb недоступен, чанк не падает и не ретраится: данные
  уже сохранены, а прогресс интерфейс подтянет опросом.
- **Публичный канал `imports`** — в событиях только UUID и числа, а весь интерфейс и так закрыт
  basic-авторизацией. Приватный канал потребовал бы пользователей и сессии, которых в задании нет.
- **Откат на опрос.** Если WebSocket не подключён — интерфейс раз в 2 секунды опрашивает
  `GET /api/imports/{id}`. Пока файл ещё читается и общее число строк неизвестно — тоже.
- **Echo без переменных сборки.** Ключ Reverb берётся из `<meta>`, хост и порт — из адреса
  страницы (nginx проксирует `/app/` в Reverb). Один и тот же собранный JS работает локально и
  в продакшене.

## 7. `id` как `numeric(20,0)` и строка в PHP

Беззнаковый bigint — это до 18 446 744 073 709 551 615. В PostgreSQL нет беззнаковых типов,
а `bigint` заканчивается на 9 223 372 036 854 775 807. `int` в PHP — тоже знаковый 64-битный.

- Колонка `rows.id` — `numeric(20,0)` и первичный ключ: он же уникальное ограничение по id из
  файла, отдельный автоинкремент не нужен.
- `RowValidator` проверяет id как строку: только цифры, ведущие нули отбрасываются, сравнение
  с максимумом — по длине, потом лексикографически. Никаких переполнений.
- Числовая ячейка Excel приходит как `float`. Принимаются только целые значения меньше 2⁵³ —
  выше `float` уже не хранит целые точно, и «12345678901234567890» тихо превратилось бы
  в другое число.

## 8. Валидация: строгие правила задания

- `name` — только `[A-Za-z ]`. Неразрывный пробел, апостроф (`O'Brien`), дефис, кириллица — ошибка:
  так сформулировано задание. Пробелы по краям обрезаются, строка из одних пробелов — ошибка.
- `date` — строго `dd.mm.yyyy` плюс `checkdate()`: `29.02.2023`, `31.04.2020`, `1.2.2020` — ошибки.
  Если ячейка отформатирована в Excel как дата, OpenSpout отдаёт `DateTime` — он приводится к
  `d.m.Y` и проходит ту же проверку.
- Все ошибки строки собираются вместе, в порядке колонок:
  `4 - id must be …, name must …, date must …`.

`RowValidator` — обычный класс без зависимостей от фреймворка, поэтому unit-тесты на него
выполняются за миллисекунды.

## 9. Воркер, который можно оставить работать надолго

- `queue:work --max-jobs=1000 --max-time=3600 --memory=256` — процесс периодически перезапускается
  (Docker `restart: unless-stopped`), так что возможные утечки памяти не накапливаются.
- У джоб задан `timeout`, у чанков — `tries = 3` и экспоненциальный `backoff` (5, 25, 125 с),
  `failed()` пишет в лог.
- `REDIS_QUEUE_RETRY_AFTER=660` больше самого длинного таймаута (600 с у чтения файла). Иначе
  Redis отдал бы ещё работающую джобу второму воркеру.
- Установлен `pcntl` — без него `timeout` джобы не работает.

## 10. Инфраструктура и качество

- **Docker:** один `Dockerfile` с целями `dev` (код монтируется, есть Composer) и `prod`
  (зависимости без dev, собранный фронтенд, OPcache без проверки файлов). Сначала копируются
  `composer.json`/`composer.lock` и ставятся зависимости, потом исходники — слой с `vendor/`
  кэшируется, пока не поменялся lock. Контейнеры работают не от root.
- **Тесты на настоящих PostgreSQL и Redis,** а не на SQLite: `ON CONFLICT`, `numeric(20,0)`,
  Lua-скрипты и `Bus::batch` ведут себя в SQLite иначе или не работают вовсе.
- **PHPUnit, а не Pest.** Он идёт со скелетом Laravel и его знает любой PHP-разработчик. Pest —
  синтаксис поверх PHPUnit, эти тесты он бы понятнее не сделал.
- **Larastan level 8.** Полная проверка типов, включая nullable. Уровни 9–10 в основном ругаются
  на `mixed` из `config()` и ответов Redis; пришлось бы расставлять касты везде без реальной пользы.

## Что можно улучшить (и почему не сделано сейчас)

- **Хранилище файлов** — локальный диск общий для контейнеров одного сервера. Для нескольких
  серверов — S3 (в Laravel это смена диска в конфиге).
- **Horizon** — удобный дашборд и автомасштабирование воркеров. Для одного воркера это лишняя
  зависимость; `queue:work` покрывает задачу.
- **Строгий порядок «первой строки» при нескольких воркерах** — см. раздел 3.
- **Пользователи и приватные каналы** вместо общего basic-auth — если появится мультитенантность.
